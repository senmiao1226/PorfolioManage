# 投资组合管理系统 · 融合汇报 PPT 大纲

> **适用场景**  
> - **课程答辩 / 项目演示**：向讲师、直属经理及公司相关利益方汇报（**3 人小组常见时长：15–20 分钟** + 提问）。  
> - 亦可用于客户与开发同场；时间紧时删掉「学习背景」「客户验收」等页即可。

---

## 一、讲好一个故事：开头 · 主体 · 结尾

| 结构 | 对应内容 | 与讲师框架的对应 |
|------|----------|------------------|
| **开头** | 团队 → 项目是什么 → **学习任务、任务要求、可用时间** → **实施思路** → **分工/协作** → **技术与工具** | 开场部分 |
| **主体** | 价值与功能概览 → **数据模型与设计思路** → **高层架构** → **现场演示** → （可选）质量与部署 | 成果展示 |
| **结尾** | **挑战与反思**（团队、难题、错误、改进）→ **未来规划** → 致谢与提问 | 挑战与反思 + 未来规划 + 结尾 |

**时间分配建议（15–20 分钟）**

| 块 | 建议时长 | 说明 |
|----|----------|------|
| 开头 | 约 3–4 分钟 | 团队、任务、分工、技术栈一带而过，不展开细节 |
| 主体 | 约 8–12 分钟 | 数据模型 + 架构 4–6 分钟，**演示 4–8 分钟**（核心） |
| 结尾 | 约 3–4 分钟 | 挑战与反思 2 分钟，未来规划 1 分钟，过渡提问 |

## 三、幻灯片逐页内容（复制到 PowerPoint / Google Slides）

以下为 **答辩优先顺序**；页号可按你删减后重排。

---

### 第 1 页｜封面

- **标题**：投资组合管理系统 — 项目演示  
- **副标题**：全栈实践（Spring Boot + Vue）· 小组汇报  
- **信息**：小组姓名（3 人）、日期、课程/部门名称、版本（如 v1.0）

**备注**：一句话说明听众：讲师、经理与相关利益方。

---

### 第 2 页｜团队介绍

- 姓名 + **角色或主要负责范围**（如：后端 API / 前端界面 / 数据库与联调 / 文档）  
- 可配小头像或 Git 贡献说明（可选）

---

### 第 3 页｜项目与学习背景

- **项目一句话**：解决什么问题（如：统一多组合持仓、行情与可视化分析）  
- **课程/学习任务**：课程要求你完成什么（全栈、REST、持久化、前后端分离等，按实际写）  
- **任务要求**：必须交付的功能或非功能点（按任务书列 3–5 条）  
- **可用时间与节奏**：总周期、每周投入、里程碑（让评委了解约束）

---

### 第 4 页｜项目实施思路

- 如何从需求到设计再到实现（迭代顺序：先核心数据与 API，再页面；或先垂直切片等）  
- **一张简图**：需求 → 模型/API → UI → 联调测试（任选）

---

### 第 5 页｜角色分工与协作方式

- **后端 / 前端** 谁负责哪些模块；或 **结对编程** 在哪些环节（写清即可）  
- 协作方式：仓库分支策略、例会、Code Review、文档谁维护（简要）

---

### 第 6 页｜使用的技术与工具

| 类别 | 示例（按项目实际填写） |
|------|------------------------|
| 后端 | Spring Boot 3、JPA、MySQL、… |
| 前端 | Vue 3、Vite、Vue Router、… |
| 数据与脚本 | MySQL、初始化 SQL、… |
| 工程化 | Git、Maven、npm、IDE、… |

**备注**：工具一页表即可，不必展开每个库的用途（留给架构页）。

---

### 第 7 页｜痛点与目标（业务语言，压缩版）

- 信息分散、估值与决策成本高、记录追溯不便（2–3 条）  
- **本项目目标**：多组合管理、行情与估值、分析可视化、可维护的全栈结构

---

### 第 8 页｜产品全景与核心功能（可合并为一页）

- **一图**：Dashboard / 组合与持仓 / 市场 / 分析  
- **要点**：多投资组合、持仓与交易、行情与价格策略、仪表盘与分析（列表级，不展开）

*时间紧时与第 7 页合并为「项目与功能概览」一页。*

---

### 第 9 页｜数据流与行情（压缩版，可选）

- 价格：主源 → 缓存 → 备用源（一句话 + 小图）  
- *若第 11 页已写清外部依赖，本页可删以省时间。*

---

### 第 10 页｜数据模型概览及设计思路（讲师要求 · 建议保留）

- **ER 简图或主要表清单**：如 Portfolio、Holding、Transaction、Instrument、Price…（按实际表名）  
- **设计思路**：为何分表、核心外键关系、与领域对象（实体）的对应  
- **一句话**：数据如何支撑「组合—持仓—标的—价格」业务链

**备注**：这是答辩常见得分点；宁可少讲功能页，也要讲清楚模型。

---

### 第 11 页｜应用高层架构

- **前端**：Vue SPA → `/api` 代理 → 后端  
- **后端**：Controller / Service / Repository（或你实际分层）  
- **数据**：MySQL + JPA；**外部**：行情 API（缓存与降级）  
- *配一张分层图：浏览器 → API → 服务 → DB / 第三方*

---

### 第 12 页｜现场演示

- **演示顺序**：Dashboard → 组合与持仓 → 市场 → 分析（按实际）  
- **旁白**：每一步对应「用户得到什么信息」  
- *本页可只列提纲，**真实时间用在投屏操作**。*

---

### 第 13 页｜质量与工程实践（可选，时间紧可口头一句带过）

- 测试、配置分环境、健康检查、文档（`README` / `PROJECT_DOCUMENTATION.md`）  
- 不必展开，体现「有工程意识」即可。

---

### 第 14 页｜挑战与反思（讲师要求 · 建议保留）

- **团队协作**：沟通是否顺畅、如何分工调整、哪些做法有效  
- **技术难题**：例如联调、JPA 映射、跨域、行情 API 限制、编码与数据库字符集等（写真实经历）  
- **犯过的错误**：可简短 1 条，说明如何纠正（体现学习）  
- **可改进的做法**：测试覆盖、错误处理、性能、安全若时间不够会怎么做  

**备注**：诚实、具体比空话加分；避免只抱怨不总结。

---

### 第 15 页｜未来规划

- **下一步产品功能**：权限、多币种、更多分析维度等（按兴趣列 2–3 条）  
- **下一步技术**：缓存策略、部署自动化、监控等  
- *标注「时间充裕时可展开」— 答辩超时则只读标题。*

---

### 第 16 页｜总结与致谢

- **总结**：目标是否达成、最大收获（业务 + 技术各一行）  
- **感谢聆听**  
- **欢迎提问**（留邮箱或仓库地址可选）

---

## 六、制作提示

1. **视觉**：业务页用截图，技术页用架构图与 ER 图；全篇色系统一。  
2. **页数**：答辩 **12–16 页** 较合适；附录另存。  
3. **分工**：可按页拆分主讲人（如一人讲开头、一人讲模型与架构、一人演示与反思），最后一页齐答。
